Selected work

Problems I solved

Silent balance saves after a framework upgrade

Problem
After a framework upgrade, affiliate wallet balances and cached stats on existing records stopped saving. There was no error and no log.
What I built
I traced it into the MongoDB ORM. It compared Decimal128 values with ==, and any two Decimal128 values are equal that way, so every change looked like "no change". I added a shared compare method for every cast of this kind. I also added a rule that tests must check a fresh read from the database, not the model in memory.
Why it mattered
Balances save again. The same bug can no longer hide in tests that only check the in-memory model.

CPU saturation on a high-traffic endpoint

Problem
One high-traffic endpoint pushed all CPU cores of a production server to full load.
What I built
I found an O(n²) loop over a large catalog and replaced the nested scan with a linear pass. I then made it a standing rule: every change states its complexity, has no collection calls inside loops, and never loads the full catalog per request.
Why it mattered
CPU went back to normal. The rule now runs on every change as part of my performance review.

Self-healing analytics sync between MongoDB and ClickHouse

Problem
Analytics data copied from MongoDB to ClickHouse for reports could drift from the source or arrive twice.
What I built
Drift self-repair for the synced data, a sync that removes duplicates, an alert when duplicates appear, query performance logging, and a short-lived read cache for report queries.
Why it mattered
Drift is found and repaired by the system. Duplicates raise an alert instead of passing silently into reports.

Marketing automation engine

Problem
Operators needed automated customer journeys and audience segments that send rewards safely, at scale.
What I built
A journey engine with trigger, profile check, action, delay, stop and conversion steps. Scheduled triggers with caps and paced sending. Pause and resume that fully freezes a journey. Customer segmentation with change tracking, showing who was added and removed.
Why it mattered
Scheduled sends are capped and paced, and each reward is paid once.

Rules with reasons

My rule files work at three levels: personal, platform and service. Each rule carries its reason and often the incident date, so the agent can apply it to cases the rule does not name.

Learning loop

Every incident becomes a rule the same day. Examples are the CPU hot path, the silent Decimal128 save, and a stale code comment that was trusted over the code.

Hard limits

The agent works under hard limits on commits, servers and private data.

Stop and ask

On any business or money decision, the agent stops, states the question in plain words, lists the options with a recommendation, and builds nothing until I answer.

Review gates

A money-safety review checks retries, redelivered messages, two workers at once, crashes between writes and reverse paths. A performance review checks reads, writes, CPU and memory per run and per day. No task closes without both.

Memory and task board

A curated memory index with topic notes. A task board the agent updates through a command-line tool and hooks, with plans, small reviewable chunks, rollout steps and open questions.

Reusable skills

Custom skills for reviews, guides, API explorers, handoffs and backups.

Testing the tool

I checked which sub-agents load my rules and changed how I brief the ones that do not.
